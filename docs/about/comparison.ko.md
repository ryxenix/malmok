# 자주 묻는 질문과 도구 비교

말목은 RKE2 구축·검증·인계에 집중합니다. 조직이 이미 운영하는 도구와 목적에 맞게 선택하십시오.

## 고객사가 서버를 이미 준비했다면 무엇을 해주나요?

바로 그 시점부터 말목의 역할이 시작됩니다. 서버가 준비되어 있어도 RKE2 클러스터
구축은 남아 있습니다. 말목은 Linux 서버에 SSH로 접근해 사전 점검, 구축 계획 확인,
설치, 중단 후 재개와 결과 리포트 생성을 수행합니다.

고객사가 제공한 서버든, 수동으로 준비했든, 자동화로 생성했든 관계없습니다.
특정 프로비저닝 도구를 먼저 사용해야 한다는 전제는 없습니다.

[준비된 서버로 시작하기 →](../getting-started/quick-start.md)

## SI·공공기관·공기업 납품에도 적합한가요? { #customer-delivery }

고객사가 Linux 서버를 제공하고, RKE2를 사용하기로 결정했으며, 공급사가 클러스터
기반 구축과 인계를 담당하는 사업이라면 검토할 수 있습니다. AI·문서처리·검색·데이터
플랫폼 등을 여러 고객사에 반복 납품하는 상황이 그 예입니다.
이는 목표 사용 상황이며, 해당 시장에서 도입 실적이 검증됐다는 주장은 아닙니다.

사전 점검은 현장별 서버·네트워크 차이를 확인하고, 재개 기능은 중단된 구축을
이어가며, 리포트는 검토·인수인계 기록을 남기는 데 사용합니다.
말목의 역할은 클러스터 기반 구축이며, 납품 솔루션 자체의 배포는 별도로 담당해야 합니다.

고객사에 이미 적합하고 지원 가능한 클러스터가 있다면 새로 구축할 필요가 없을 수
있습니다. 지정된 배포판이나 기술지원 계약 조건도 먼저 확인하십시오.
말목이 조달 적격성, 보안 인증이나 검수 요건 충족을 보증하지는 않으며,
공급사의 유지보수 책임을 대신하지도 않습니다. 리포트는 검토를 돕는 기록이지
검수 승인서가 아닙니다. 알파 단계와 검증 범위의 제한은 이 경우에도 적용됩니다.

## Terraform이나 Ansible로 구축하면 되지 않나요?

가능합니다. 이미 검증된 RKE2 자동화가 있다면 교체할 필요는 없습니다.
말목은 IaC라는 방식을 대체하는 도구가 아니며, 말목의 `cluster.yaml`도 선언형
구성입니다. RKE2 구축에 필요한 흐름을 직접 작성하고 유지하는 부담을 줄이는 것이 목적입니다.

서버와 네트워크가 이미 준비됐다면 별도의 프로비저닝 단계는 필요 없을 수 있습니다.
다만 서버 구성과 클러스터 설치는 남아 있습니다. 말목은 인프라를 준비한 방법과 무관하게
그 단계부터 사용할 수 있습니다.

여러 소프트웨어와 OS 상태를 관리하는 범용 구성 관리에는 Ansible이 적합합니다.
말목은 RKE2 문서 검증, 호스트와 노드 간 통신 실측, 계획 검토, 재개 가능한 실행과
인계 리포트를 한 흐름으로 제공합니다.

함께 사용할 수도 있습니다. 기존 자동화로 머신과 현장 정책을 준비하고,
SSH로 접근 가능한 호스트를 말목에 전달하십시오.

## k0sctl과 무엇이 다른가?

[k0sctl](https://github.com/k0sproject/k0sctl)은 가장 가까운 선행 도구입니다.
선언형 문서로 k0s를 구축·관리하며 업그레이드와 에어갭 자재도 지원합니다.
대상 배포판이 k0s라면 k0sctl이 적합합니다.

말목은 RKE2를 대상으로 호스트 준비, Cilium 또는 대체 데이터플레인, Gateway API,
PKI, GitOps와 관측을 연결합니다. 온라인과 에어갭 실행에서 실측 결과와 실행 근거를 기록합니다.

## CAPRKE2로 하면 되지 않나?

[CAPRKE2](https://caprke2.docs.rancher.com/)는 Cluster API의 bootstrap 및
control-plane provider입니다. 관리 클러스터와 인프라 provider, 지속적인
Cluster API 조정을 이미 운영한다면 CAPRKE2가 더 적합할 수 있습니다.

말목은 SSH 가능한 기존 머신에서 출발합니다. 운영자 머신의 단일 바이너리로
실행하며 말목 전용 관리 컨트롤러나 노드 에이전트를 남기지 않습니다.

## 업무용 프로덕션 환경에 바로 써도 되나요?

현재 알파 단계입니다. 구축 성공 사례가 모든 토폴로지와 네트워크에서의 프로덕션
준비 완료를 뜻하지는 않습니다. [검증 매트릭스](../40-verification-matrix.md)와,
해당하는 경우 [에어갭 지원 조건](../guides/air-gap.md)을 확인하십시오.
도입 전 실제 사용 환경과 복구 절차를 검증해야 합니다.
문서 스키마는 `v1alpha1`이며 마이너 릴리스 사이에 바뀔 수 있습니다.

## 어디까지 담당하나요?

다음 작업은 현장 인프라와 애플리케이션 소유자의 역할입니다.

- 머신, 네트워크와 DNS 존 생성
- 방화벽 정책 변경
- 애플리케이션 `HTTPRoute` 생성과 워크로드 배포
- 구축 후 알림과 지속적인 운영

말목은 클러스터 기반을 구축하고 인계합니다.
